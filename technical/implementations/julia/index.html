Julia is the third independent calculation engine in the current Multiphysics architecture. Its FDM, FEM and fixed-geometry FVM paths have native execution evidence against four frozen engine-neutral reference cases. Geometry-changing FVM remains unpromoted. Project-current performance is CANONICAL_MEASURED under the governed P1/P2 campaign, while cross-engine agreement remains implementation-verification evidence rather than experimental validation.

2. Engine independence

Julia is not a wrapper around GNU Octave or C++. The three engines consume common resolved inputs and emit equivalent result histories while implementing method-specific numerical work independently.

That separation supports independent implementation evidence for the same mathematical method and later comparison of language/runtime trade-offs after equivalent numerical behaviour has been established.

No engine is designated as numerical truth or as the permanent backend of another.

3. Solver-ready input boundary

Julia consumes already-resolved engine-neutral cases containing geometry, material laws, sources, boundary/interface data, electrical input, initial state and temporal configuration.

Four current reference cases are frozen as common implementation targets. They are numerical verification inputs, not experimental-validation datasets and not golden outputs from another engine.

4. Package and environment

The Julia implementation separates input/output contracts, material-property evaluation, shared thermal and electrical closures, temporal integration and independent spatial solvers.

The current native verification was executed under Julia 1.13.1 with a recorded software environment. That environment belongs to the reproducibility record; it is not a performance claim.

5. Shared temporal and physical contracts

FDM, FEM and FVM reuse Julia-level representations of project concepts that are genuinely shared, including material-property evaluation, lateral heat exchange, distant-end Robin closure, thermal-contact behaviour, interface electrical-power partition, Forward Euler and Adams–Bashforth 2.

The spatial method remains independent from those shared contracts.

6. FDM native evidence

The Julia FDM path passed native package verification across all four frozen reference cases. It also produced engine-neutral histories that were compared, method for method, with independently generated C++ and GNU Octave histories.

This is numerical and software verification evidence, not physical validation of flash-butt welding.

7. FEM native evidence

The Julia FEM path follows the accepted P1 Galerkin formulation with two-point Gauss integration, row-sum mass lumping, cell-centred half-cell completion and shared physical boundary/interface laws.

Its native verification passed the same four reference cases and same-method comparison with independently generated C++ and GNU Octave FEM histories. The evidence remains method-scoped.

8. Output and multi-engine post-processing

Julia results enter the same engine-neutral post-processing boundary used for the other engines. Histories are validated before comparison, explicitly supplied case/method/engine coverage can be inventoried without choosing a golden engine, and absent histories remain explicitly absent rather than being inferred or repaired.

9. Fixed-geometry FVM native evidence

The Julia FVM path uses harmonic face conductivity, conservative face-flux differences and the same shared thermal and temporal layers. Its native verification passed the frozen fixed-geometry reference cases and same-method comparison against independent C++ and GNU Octave histories.

Geometry-changing FVM remains unpromoted. Fixed-geometry verification does not promote flashing, upsetting or whole-process workflow parity.

10. Performance boundary

No public Julia performance advantage is claimed. Project-current performance is CANONICAL_MEASURED under PERFORMANCE.STATUS.GOVERNANCE.2026-10-06.R1, backed by canonical campaign PERFORMANCE-MULTI-ENGINE-20261005-232449Z.

That status means the governed measurements exist; it does not make Julia universally faster, authorize an overall engine ranking or provide experimental validation. The campaign keeps fresh-process latency (P1) separate from warmed in-process throughput (P2) because startup and JIT costs answer a different question from steady execution.

11. Verification is not validation

The current Julia evidence supports statements about implementation consistency. It does not establish experimental agreement with the physical welding process.

Agreement with C++ or Octave is not experimental validation, FDM/FEM agreement is not an exact-solution proof, frozen reference cases are not calibration datasets, and successful numerical verification does not itself authorize a public release.

Physical calibration and independent experimental validation remain separate evidence horizons.

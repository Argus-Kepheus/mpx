GNU Octave is one of the active sibling calculation engines of the Multiphysics project. It currently has the broadest process-workflow coverage, but this does not make it the scientific reference or permanent primary engine. This page describes public software architecture and execution concepts without exposing repository-internal workflow labels.

1. Role in the project

GNU Octave is the original calculation environment and remains an active sibling of the C++ and Julia engines. Numerical method identity remains independent from engine identity: FDM, FEM and FVM are spatial methods, while GNU Octave is one implementation environment capable of hosting them.

Octave is retained because its MATLAB-compatible language and high-level matrix and vector operations make numerical prototyping, diagnostics and scientific inspection straightforward. Its broad workflow coverage complements the compiled/runtime-control role of C++17 and the high-level JIT scientific-computing role of Julia. These are complementary engineering characteristics, not a ranking of scientific validity or performance.

FDM and FEM are implemented. FVM is implemented and verified for the fixed-geometry/current-heating scope. It also runs Maturity-1 Flashing with partial front control volumes, numerically verified under ADR 0036. Maturity-0 Flashing and geometry-changing Upsetting/Pressing remain unpromoted.

2. Method-neutral execution

The Octave architecture uses a method-neutral execution layer. A simulation context combines the selected spatial method, a resolved physical case, numerical execution choices and the appropriate solver implementation without collapsing those concepts into one object.

The same process orchestration can therefore advance different spatial discretisations while preserving common process chronology, state transfer and temporal-integration rules.

3. Solver selection and extensibility

A central solver registry connects method identities to their implementations and declared capabilities. Adding another spatial method is intended to introduce another solver implementation rather than adding method-specific branches throughout shared physics and process logic.

4. Shared solver interface

Each spatial method exposes the common information needed by the process layer: method identity, resolved case, numerical configuration and a step operation. The process layer depends on that shared interface rather than on a hard-coded FDM, FEM or FVM implementation.

5. Process orchestration

The shared process engine owns chronology, state chaining, remapping and event handling, sampling and stage dispatch. A spatial solver supplies the method-specific spatial update.

Schedule-oriented studies therefore reuse one process orchestration layer instead of maintaining a complete process sequence separately for every numerical method.

6. Method-specific and shared numerical services

Spatial discretisation remains method-specific, while interpolation, meshes, remapping, boundary/interface support and temporal integration can be shared when their governing assumptions are method-neutral.

The current temporal layer supports Forward Euler and Adams–Bashforth 2 with explicit starter/restart semantics. Private integrator memory remains distinct from the physical state and scientific process history.

7. Physical and numerical ownership

The calculation engine does not own the universal definitions of materials, physical interface laws or process-stage meaning. Those are project-level model concepts resolved before or alongside numerical execution.

Changing from FDM to FEM should therefore change the spatial discretisation, not the identity of the workpieces, material laws, thermal-contact law, distant-end condition or process schedule.

8. Verification surfaces

The Octave implementation is checked at both architecture and numerical-method levels. The verification surface covers solver selection, process-sequence consistency, compatibility of supported execution paths, FDM conservation and refinement behaviour, and FEM assembly and stability references.

Those checks are implementation and numerical evidence. They are not experimental validation of the physical welding model.

9. Relationship to C++ and Julia

GNU Octave, C++ and Julia are independent sibling engines. None obtains its numerical result by calling another engine. Same-method cross-engine comparison is performed only after each engine has produced its own history.

Julia FDM, FEM and fixed-geometry FVM have native verification evidence across four frozen engine-neutral reference cases with same-method comparison against the other engines. Geometry-changing Julia FVM remains unpromoted. 10. Current limitations and publication boundary

Octave currently has the broadest process-workflow coverage, but this does not imply that every numerical method has equal stage coverage or equal verification maturity.

The public website presents the scientific architecture, verified scope and capability boundaries. Repository paths, campaign identifiers, internal workflow labels and restricted data remain part of the private implementation and evidence layer rather than the public explanatory surface.

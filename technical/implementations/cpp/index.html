The C++ engine is an active sibling calculation engine of GNU Octave and Julia. It provides an independent compiled implementation of selected Multiphysics formulations. Narrower workflow coverage does not make its architectural role secondary.

1. Purpose and maturity

The C++ engine provides independent implementations of selected numerical formulations so that the same resolved physical and numerical problem can be executed in more than one language and compared only after each engine has produced its own result.

Its present scope includes resolved-case FDM, FEM and FVM paths. Whole-process workflow coverage remains narrower than GNU Octave. Implementation coverage, numerical verification, benchmark maturity and experimental validation are treated as separate concepts.

2. Language and runtime role

The current engine targets C++17. Ahead-of-time compilation provides explicit control over types, data layout, compiler settings and standalone runtime packaging, with a natural path toward deployment and high-performance-computing studies when those become scientifically justified.

The project also uses C++ as an independent implementation surface for LLM-assisted code generation, review and cross-checking. These are architectural advantages, not evidence that C++ is scientifically superior or faster than another engine before equivalent benchmarking.

3. Architectural organisation

The public architecture separates common engine contracts and orchestration, shared physical and numerical closures, method-neutral temporal integration, independent FDM/FEM/FVM spatial implementations, and engine-neutral input/output boundaries.

The implementation details remain native to C++; it does not call GNU Octave or Julia for spatial derivatives or time steps.

4. Method and engine remain separate

FDM, FEM and FVM are numerical methods. C++ is an implementation environment.

5. Solver-ready input boundary

Cross-engine studies begin from already-resolved, engine-neutral cases containing numerical geometry, temporal settings, boundary and interface data, source terms, initial state and resolved material-property laws.

High-level material taxonomy, publication configuration and plotting concerns remain upstream from this solver-ready boundary. This prevents an engine from silently redefining the scientific input while being compared with another implementation.

6. Independent temporal integration

Implementation-specific temporal memory is not exchanged between engines. Each engine initialises and advances the configured temporal method independently.

The C++ temporal layer supports Forward Euler and Adams–Bashforth 2 with explicit starter and restart behaviour, while remaining independent from the selected spatial method.

7. FDM path

The C++ FDM implementation independently represents the active cell-centred conservative flux formulation, including the promoted positive-conductivity reconstruction and shared physical boundary/interface meaning.

8. FEM path

The C++ FEM path independently represents the current linear P1 Galerkin formulation with two-point Gauss quadrature, row-sum mass lumping, cell-centred half-cell completion and the same model-level boundary/interface laws.

9. FVM path

The C++ FVM path uses a cell-centred control-volume formulation. Fixed-geometry work is implemented within the currently verified scope; broader geometry-changing welding capability remains a separate promotion boundary.

10. Result-history boundary

Resolved-case runs produce an engine-neutral temperature history suitable for post-processing and same-method comparison. Development parity histories are deliberately distinguished from authoritative performance benchmark results.

11. Cross-engine comparison

Same-method comparison between independently executed engines is the principal software-parity question. Cross-method comparison, such as FDM versus FEM, is a different numerical-verification question because different discretisations need not produce identical values on a fixed coarse mesh.

Current comparison tolerances are verification gates rather than claims about physical validation or performance superiority.

12. Verification and benchmark boundary

The C++ verification surface covers common engine operations, the three spatial methods, shared physical closures, temporal integration, input/output handling and resolved-case execution.

The project-current public performance claim is now limited to the accepted canonical P1/P2 campaign, where equivalent cases, numerical acceptance criteria, compiler/runtime identity, machine conditions, warm-up rules and timing scope were frozen and executed under the reproducible protocol. P1 fresh-process latency and P2 warm in-process throughput remain separate measurement modes; no combined score, overall engine ranking or universal speed claim is authorized.

13. Relationship to GNU Octave and Julia

GNU Octave, C++ and Julia are active sibling engines. Their differing languages and runtime models provide implementation diversity while preserving common scientific contracts.

Julia FDM, FEM and fixed-geometry FVM have native verification evidence across four frozen engine-neutral reference cases with same-method comparison against C++ and Octave. Geometry-changing Julia FVM remains unpromoted. Cross-engine agreement is implementation-verification evidence. It is not proof that the shared physical model has been experimentally validated.

14. Current limitations and publication boundary

The C++ engine remains narrower than GNU Octave in whole-process workflow coverage. Its resolved-case paths should not be presented as complete process parity.

The public website presents architecture, capability and evidence boundaries. Repository paths, internal campaign names, raw artifact identifiers and development workflow labels remain in the private engineering record rather than the public explanatory surface.

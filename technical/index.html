Living technical documentation

Technical

This section provides a living overview of the current mathematical, numerical and computational state of the Multiphysics project.

It documents the present project state. The current numerical baseline is reconciled, but this locally buildable website artifact is not itself a release authorization. Formal dissertations, papers and releases remain independent transactions.

Numerical formulation

Spatial methods

technical preview

FDM — 1D

Current cell-centred finite-difference formulation, physical closures, semi-discrete system, time-integration relationship and verification evidence.

 technical preview

FEM — 1D

Current cell-centred P1 Galerkin formulation, including weak form, element assembly, mass lumping, half-cell completion, physical flux coupling and stability reference.

 implemented / limited scope

FVM — 1D

The 1D finite-volume solver has an implemented-and-verified fixed-geometry/current-heating path and, in GNU Octave, a numerically verified Maturity-1 Flashing path (ADR 0036). Maturity-0 Flashing and geometry-changing Upsetting/Pressing remain unpromoted; none of these paths is presented as experimentally validated.

Implementations

Calculation environments

active sibling

GNU Octave

An active sibling engine with the broadest current process-workflow coverage. MATLAB compatibility and high-level matrix/vector operations make it useful for numerical development, inspection and scientific prototyping.

 active sibling

C++

An active independent C++17 sibling engine used for same-method cross-engine verification, explicit compiled implementations and LLM-assisted development. Its current workflow coverage is narrower than Octave, but its architectural role is not secondary.

 FDM/FEM/FVM fixed-geometry native verification passed

Julia

Julia FDM/FEM/FVM fixed geometry passed native verification against four frozen engine-neutral reference cases, including neutral history ingestion and same-method cross-engine parity. Geometry-changing Julia FVM remains unpromoted. P1/P2 performance is measured within the recorded cases, machine and toolchains.

Scientific tooling

Automation and evidence infrastructure

active supporting tooling

Python

Python supports validation, governance, material-data workflows, package isolation, provenance, semantics, diagnostics and neutral cross-engine comparison. It is supporting scientific infrastructure, not a calculation engine.

 multi-engine consolidation validated

Post-processing

Recorded temperature histories use a neutral post-processing contract. Histories are validated before protected comparisons, and the multi-engine inventory remains deterministic without choosing a golden engine.

Evidence and validation boundaries

technical preview

Verification framework

How analytical/reference cases, conservation, refinement, cross-method and cross-engine evidence fit together without being confused with experimental validation.

 current baseline reconciled

Numerical verification

FDM/FEM have a current native attestation, fixed-geometry FVM remains verified, and four engine-neutral resolved reference inputs are frozen as implementation targets. These facts remain distinct from experimental validation.

 future evidence

Experimental validation

Physical calibration and an independent validation case require traceable experimental observables and uncertainty treatment; the complete FBW model is not currently presented as experimentally validated.

This website presents the publishable scientific state of the Multiphysics project. It does not expose private correspondence, internal researcher profiles or unpublished collaborative material.

The Multiphysics project separates numerical verification from physical validation. Numerical verification asks whether a mathematical and discrete formulation is implemented consistently and whether its numerical behaviour is understood. Physical validation asks whether the resulting model represents measured behaviour of the real process within a declared scope and uncertainty.

Agreement between two numerical methods or two programming-language implementations is useful evidence, but it is not experimental validation.

Evidence layers

The current verification strategy is deliberately layered. Different checks answer different questions and none is treated as a universal substitute for the others.

  • Model contracts and invariants define units, signs, conservation meaning, boundary/interface meaning and state-transfer semantics.
  • Method-level checks exercise discrete operators, assembly, sources, boundary closures, stability references and limiting cases.
  • Analytical and manufactured/reference cases compare numerical output with fields or balances known independently of another solver.
  • Conservation checks verify integrated energy or flux behaviour when the continuous problem supplies a conservation statement.
  • Spatial and temporal refinement asks whether discrepancies decrease as resolution is refined.
  • Cross-method comparison compares independent discretisations of the same continuous problem without designating one as exact.
  • Cross-engine comparison compares independent software implementations of the same method using equivalent resolved input.
  • Regression tests preserve corrections for previously identified defects.
  • Physical calibration and validation use traceable real-world observables and remain separate from synthetic numerical-verification cases.

Why three independent calculation engines?

GNU Octave, C++17 and Julia are maintained as sibling calculation environments rather than choosing one language as numerical truth. Octave favours transparent scientific inspection and broad workflow coverage; C++17 provides ahead-of-time compiled runtime control; Julia combines high-level scientific expression with type-specialised JIT compilation.

The engines consume common resolved scientific inputs while keeping their numerical implementations independent. Same-method agreement can therefore reduce the risk of implementation-specific defects, while disagreement supplies a diagnostic target.

Agreement still cannot prove the shared physical model: a modelling, input or boundary/interface error may be reproduced by all engines. Cross-engine parity is implementation-verification evidence, not experimental validation.

No engine is a golden reference and no language is ranked in advance. The accepted P1/P2 campaign measures fresh-process latency and warmed throughput separately because startup/JIT and steady compute cost are different questions. Project-current performance is CANONICAL_MEASURED within the recorded cases, machine, toolchains and timing modes. These measurements do not authorize an overall engine ranking or a universal speed claim.

Current native and reference-case baseline

The current accepted FDM/FEM native verification provides a PASS for the tested numerical snapshot and remains implementation/numerical evidence rather than experimental validation of flash-butt welding.

Fixed-geometry FVM retains its implemented-and-verified status. Maturity-1 Flashing on FVM is numerically verified under ADR 0036: its refinement campaign converges to the FDM/FEM limit. Maturity-0 Flashing and geometry-changing upsetting remain unpromoted on FVM.

Four already-resolved, engine-neutral reference cases are frozen as common implementation targets:

  • a constant/asymmetric baseline with Adams–Bashforth 2;
  • the corresponding Forward-Euler variant;
  • a positive thermal-contact-resistance case;
  • a heterogeneous-material and unequal-spacing case.

These are frozen inputs, not golden outputs from Octave, C++ or Julia and not physical-validation datasets.

Post-processing and publication provenance

Recorded temperature histories enter an engine-neutral post-processing boundary. Summaries retain scientific identity such as case, engine, method and temporal integrator, while comparisons first validate the supplied histories before computing cross-engine quantities.

The downstream layer can represent partial case/method/engine coverage without choosing a golden engine. Missing histories remain explicitly missing rather than being repaired or inferred.

Experimental overlays remain downstream of the experimental-data contract and must preserve measurement identity, time/location semantics, uncertainty, processing history and publication rights. A plot does not promote an unadjudicated dataset or turn calibration data into independent validation.

Reproducibility and release boundary

The project keeps native execution evidence and frozen implementation targets as distinct reproducibility objects. A numerical PASS applies to the source and conditions actually exercised, while frozen inputs define a reusable target for independent implementations.

Neither fact grants release authorization. A numerical PASS, frozen case, generated history or locally buildable website does not by itself authorize publication. Public deployment remains a separate reviewed transaction with rights and private-export checks.

FDM verification evidence

The finite-difference verification surface includes conservative shared-face construction, boundary-flux accounting, positive reconstructed conductivity, constant-conductivity limits, equilibrium of a linear temperature field, manufactured-solution refinement, cell-centred Robin closure, steady Robin refinement, interface-source convergence and energy conservation.

The manufactured variable-conductivity study accepts an observed global convergence floor of 1.9. This is why the public FDM page describes fourth-order internal stencil ingredients without claiming that the complete active operator is globally fourth order.

These checks show what the project verifies. They do not imply experimental validation of the complete process model.

FEM verification evidence

The finite-element verification surface covers assembly, physical-domain accounting and explicit-time stability references.

The checks include recovery of physical-domain thermal capacity and volumetric source under the half-cell completion, equivalence of vectorised and elementwise assembly, the constant-property lumped-mass stability reference, Robin boundary behaviour and cross-method FDM/FEM diagnostics.

The FDM/FEM comparison is deliberately a diagnostic, not a regression tolerance. Complete space-time histories are compared symmetrically and neither method is treated as the exact reference.

Controlled cross-method studies

A broader method-neutral verification programme asks whether FDM, FEM and FVM solve the same one-dimensional thermal problem consistently before physical calibration.

The controlled cases separate equilibrium, cooling, bimaterial behaviour, Joule heating and post-heating redistribution. Synthetic heterogeneous material data are used only for numerical verification and are not presented as calibrated steel data.

The quantitative refinement tier uses successive spatial resolutions with a common method-independent timestep chosen from the most restrictive active stability reference. No method is designated as exact.

Cross-method and cross-engine questions are different

Cross-method comparison asks whether different spatial discretisations approach the same continuous problem. FDM and FEM are therefore not expected to produce identical numbers on a fixed coarse mesh.

Cross-engine comparison asks whether independent software implementations of the same method produce sufficiently consistent output for equivalent resolved input. Each engine computes its own result before a neutral comparison is performed.

Current same-method tolerances are development verification gates. Cross-language agreement is implementation-verification evidence; a defect shared by all engines would still be a defect.

Regression evidence

Regression checks permanently preserve corrections after a specific defect has been identified. This is intentionally distinct from analytical or manufactured-solution correctness and from generic per-method verification.

Manufactured-solution programme

The project is progressively organising method-independent manufactured-solution problems with known analytical fields and source terms.

FDM and FEM already use manufactured/reference reasoning in their verification surfaces, while broader common manufactured-solution coverage remains an ongoing verification layer rather than a completed universal claim.

Physical calibration and experimental validation

Physical calibration and validation are intentionally outside the numerical-verification studies. Calibration first requires defensible observables and sensitivity/identifiability analysis before several entangled parameters are tuned.

Candidate observables include interface or near-interface thermal histories, electrical power, burn-off and stage timing, but only quantities supported by traceable source data should enter an objective function.

A defensible validation programme requires uncertainty treatment and an independent validation case. The website therefore does not claim that the complete flash-butt-welding model is experimentally validated.

Publication rule for verification claims

A future public verification result should identify the problem definition, physical inputs, numerical controls, method and engine, spatial/time resolution, reference or comparison basis, error metrics, acceptance rule when one exists, and the reviewed scientific scope.

A diagnostic without a rigid tolerance should remain labelled as a diagnostic. Cross-engine parity should not be presented as physical validation, and a calibration case should not be reused as its own independent validation case.

Current public interpretation

The present project state supports a substantial numerical-verification programme for the one-dimensional thermal model. FDM and FEM have accepted native execution evidence, fixed-geometry FVM remains verified, and four engine-neutral resolved inputs are frozen as common implementation targets.

Method-independent manufactured-solution work and broader verification suites remain ongoing. Experimental calibration and independent physical validation remain separate future work and will only be promoted when traceable experimental observables, uncertainty treatment and an independent validation case support those claims.

This website presents the publishable scientific state of the Multiphysics project. It does not expose private correspondence, internal researcher profiles or unpublished collaborative material.
